但它的影响会像一颗石子扔进池塘，涟漪会扩散到 3 层：后端序列化层 → 前端展示层 → 用户操作层。

二、必须先理解：@Sensitive 到底做了什么？

它是 Jackson 的"拦截器"

@Sensitive 本身是一个空壳注解，真正的逻辑在 SensitiveJsonSerializer 类里。这个类继承了 Jackson 的 JsonSerializer，会在 Java 对象转 JSON 字符串的时候介入。

文件角色一句话
annotation/Sensitive.java 标记 "这个字段需要脱敏"
enums/DesensitizedType.java 规则 "手机号=中间4位变****"
serializer/SensitiveJsonSerializer.java 执行 "真的执行正则替换"

脱敏的核心逻辑

public class SensitiveJsonSerializer extends JsonSerializer<String> {

    @Override
    public void serialize(String value, JsonGenerator gen, ...) throws IOException {
        if (desensitization()) {
            // 需要脱敏：13812345678 → 138****5678
            gen.writeString(desensitizedType.desensitizer().apply(value));
        } else {
            // 不需要脱敏：返回原文
            gen.writeString(value);
        }
    }

    private boolean desensitization() {
        LoginUser securityUser = SecurityUtils.getLoginUser();
        return !securityUser.getUser().isAdmin();   // 管理员不脱敏！
    }
}

🛡 管理员不脱敏

代码第 52 行：return !securityUser.getUser().isAdmin();。管理员登录 → 返回 false → 不执行脱敏 → 看到完整的 13812345678。普通用户登录 → 返回 true → 执行脱敏 → 看到 138****5678。

什么时候生效？什么时候不生效？

场景是否走 Jackson 序列化？@Sensitive 是否生效？
Controller 返回 JSON（list、getInfo）走▶ 生效！
Controller 接收 JSON（add、edit）不走（反序列化）不生效
Excel 导出（export）不走（ExcelUtil）不生效
存数据库不走不生效

五、风险点：编辑表单的脱敏回填

问题复现路径

  1. 普通用户 → 打开列表 → 看到 138****5678
  2. 点击"修改" → 编辑框显示 138****5678（因为 getInfo 返回的是脱敏数据）
  3. 用户只改了其他字段（没改电话）→ 点"确定"
  4. 提交 PUT，receiverPhone: "138****5678" → ****被写进数据库

方案对比

方案做法改动量是否推荐
A. 不改 前提：普通用户没有编辑权限（Controller 有 @PreAuthorize 保护） 0 ✅ 如果权限已保护
B. 前端处理 编辑时如果 phone 包含 ****，先清空提示用户重新输入 前端改 Vue 可以但魔幻
C. 后端分离接口 getInfo 不走脱敏（单独写 VO 或去掉 @Sensitive），list 保留脱敏 后端加 VO 类 ✅ 推荐，改动可控
D. 只脱敏不编辑 前端编辑表单中"收件人电话"改为只读展示，不让编辑 前端改 Vue 业务上可能不合理

当前项目 Controller 上有 @PreAuthorize("@ss.hasPermi('crm:crmInvoiceTitle:edit')") 保护。如果编辑权限只分配给管理员角色，则方案 A 已经是安全的。
